## Export contract

### 1. Schema first
Export:
- sqlite_master table DDL
- index DDL
- table_list metadata
- table_info for every user table

Do not synthesize schema from source files when live sqlite_master is available.

### 2. Table inventory
Exclude SQLite internal objects only when clearly internal:
- sqlite_sequence
- other sqlite_* implementation tables

All application/user tables returned by live sqlite_master must be included.

### 3. Exact row counts
Before data export, record COUNT(*) for every exported table.

Manifest fields:
- table
- row_count
- primary_key columns
- WITHOUT ROWID flag if available
- export pagination mode
- chunk_count
- exported_row_count
- chunk hashes
- final table hash

### 4. Pagination
Never use unbounded SELECT.

Preferred order:
1. declared PRIMARY KEY
2. composite PRIMARY KEY tuple order
3. INTEGER rowid when table supports rowid
4. deterministic full-column order only as last-resort design requiring explicit proof

Do not use OFFSET for large-table final export if a stable keyset cursor is available.

Each request must:
- use a server-owned table allowlist
- use a bounded chunk size
- return next cursor generated by the server
- reject arbitrary SQL
- reject arbitrary ORDER BY expressions

Recommended initial chunk ceiling:
- <= 500 rows
- <= 512 KiB serialized response

Actual ceiling may be reduced if response/time evidence requires it.

### 5. Binary / numeric fidelity
Serialization must distinguish:
- null
- integer
- real
- text
- blob

BLOB must not be lossy UTF-8 converted.
Use deterministic base64 representation plus an explicit type tag if BLOB values exist.

Large integer fidelity must be tested. Do not silently round values through JavaScript Number if outside safe integer range.

### 6. Deterministic chunk integrity
For every chunk record:
- table
- cursor_before
- cursor_after
- row_count
- payload SHA-256
- first key
- last key

Local collector persists each chunk immediately.
Resume must reuse verified chunks and continue from the last confirmed cursor.

### 7. Final table integrity
For every table verify:
- source COUNT(*) == exported row count
- no duplicate exported keys
- monotonic cursor
- all chunk hashes valid

If a stable primary key exists, compute a deterministic rolling/table hash from canonical serialized rows.

### 8. Snapshot consistency
A multi-request export is not automatically one database snapshot.

Therefore final cutover export requires a short writer freeze:
1. disable/pause all known Sites DB writers/schedulers
2. verify no active write job/lease where applicable
3. capture pre-export table counts/freshness
4. perform complete export
5. capture post-export table counts/freshness
6. require pre/post equality
7. keep Sites writer frozen until target import + integrity check reaches an approved checkpoint

A writer freeze is NOT authorized by this R3 design stage.

### 9. Two-pass strategy
Optional first pass while Production remains live:
- schema
- table sizes
- pagination validation
- non-authoritative rehearsal export

Authoritative final dump:
- must occur during approved write freeze
- must start from an empty local export set or revalidate every reused chunk against the frozen source state

Do not call a live rehearsal dump the final backup.

### 10. Sensitive data
Do not expose samples from user-sensitive tables in logs/evidence.

Full export necessarily preserves database contents, but:
- raw dump/chunks remain local/private
- no DB rows in GitHub
- no DB rows in chat
- Evidence contains only counts/hashes/metadata

### 11. One-time auth
Reuse the R2 one-time migration-auth pattern:
- temporary secret
- dedicated export endpoint only
- expiry
- fail-closed
- no secret logging
- remove secret and endpoint after export

### 12. Cleanup
After successful export:
- remove endpoint
- remove temporary secret
- deploy clean Sites version
- verify export endpoints 404
- verify public site/writer state according to the approved freeze/cutover plan
