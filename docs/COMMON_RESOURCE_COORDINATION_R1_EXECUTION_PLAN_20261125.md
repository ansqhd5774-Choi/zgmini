# ZGMINI 공통 자원 보호·동시 작업 충돌 방지 실행계획 R1

기준일: 2026-11-25
프로젝트: ZGMINI Common Resource Coordination R1
담당: 공통 프로세스 총괄·자동화 담당자

## 1. 최종 목표

여러 담당자·GitHub Actions·Controller·Writer가 동시에 작업하더라도 실제 공유 자원의 충돌을 방지한다.

다음 두 조건을 함께 충족해야 한다.

1. 동일 자원의 위험한 변경은 충돌 없이 처리한다.
2. 서로 독립적인 작업은 기존처럼 병렬 실행한다.

새로운 승인 Gate나 거대한 전역 잠금 시스템을 만드는 것이 목적이 아니다. 기존 보호 기능의 공백·중복·과도한 차단을 필요한 범위에서 개선한다.

## 2. 저장소와 작업 경계

| 구분 | 저장소·브랜치 | 담당 내용 |
| --- | --- | --- |
| 본체 | `zgmini` / `codex/common-resource-coordination-r1-20261125` | 공통 계약, 실행·게시 연결, 기능 측 보호 |
| PC 제어 | `zgmini-pc-control` / 동일한 브랜치명 | Controller·설치·복구·자동화 연결 |
| 기존 기술 원본 | `codex/w03-r54-integration-master-20261125`, PR #1580 | 기술·시험·개발 계보 보존 |

두 전용 브랜치는 착수 시 원격 존재를 확인한다. 없다면 각 저장소 최신 `main`에서 생성한다.

기존 R54 브랜치 전체를 병합하거나 복사하지 않는다. 검증된 보호 원리와 필요한 모듈만 재사용한다.

현재 문서는 실행계획이다. 브랜치 생성·코드 구현·운영 적용 완료를 의미하지 않는다.

## 3. 설계 기준

### 3.1 잠금보다 자원과 효과를 먼저 정의한다

각 작업이 실제로 무엇을 읽고 변경하는지 확인한 뒤 보호 방식을 선택한다.

| 자원 | 우선 적용 방식 |
| --- | --- |
| 각자의 개발 checkout | 작업 트리 분리·정규 Git 통합 |
| 동일 원격 브랜치 | 최신 HEAD 확인·충돌 검증·정규 갱신 |
| 동일 운영 소스 묶음 | 실행 버전 고정·설치와 실행의 조정 |
| Controller 설치 대상 | 기존 설치·복구 lease 재사용 |
| Writer 설치 대상 | 기존 정상 종료·설치·복구 절차 재사용 |
| SQLite | 기존 트랜잭션·일관된 읽기 경로 |
| D1 공개 결과 | 기존 키별 CAS·게시 계약 |
| 원장·checkpoint 파일 | 기존 원자적 저장·소유권·버전 비교 |
| 공급자 호출 예산 | 기존 공통 호출량 보호 |

서로 다른 파일이라도 같은 배포본·설정·checkpoint를 구성하면 하나의 변경 단위일 수 있다. 반대로 동일 DB를 사용한다는 이유만으로 모든 읽기·계산을 직렬화하지 않는다.

### 3.2 협조하는 실행기끼리만 보호되는 한계를 명시한다

lease 파일을 만들었다는 사실만으로 임의 편집기나 비참여 프로세스의 변경까지 차단됐다고 주장하지 않는다.

각 자원에서 다음을 확인한다.

- 참여하는 모든 변경 경로
- 실제 변경 직전에 수행하는 소유권 검사
- 검증 이후 교체 경합을 막는 방법
- 우회 가능한 미참여 경로의 존재

실행 중인 소스를 바꾸지 않는 구조와 검증된 버전 고정을 우선한다. Windows 파일 핸들 유지와 디렉터리 이동의 충돌은 실제 격리 시험으로 확인한다.

### 3.3 정상 대기를 장애로 표현하지 않는다

- 자원 사용 중: 해당 변경만 대기
- 독립 작업: 계속 실행
- 도구 접근 실패: 해당 관측의 `AUTOMATION_BLOCKED`
- 실행 결과 불명: 원장·checkpoint 재조회
- 실제 무결성 실패: 해당 자원 변경 중단

시간 경과나 heartbeat 누락만으로 잠금을 자동 삭제하지 않는다.

## 4. 실행 단계 — 7단계

### 1단계. 주요 자원과 기존 보호 기능 확인

두 저장소의 실제 진입점을 기준으로 조사한다. 저장소 전체 이력이나 무관한 기능을 반복 분석하지 않는다.

우선 확인 대상:

- R54 Source Lease와 R78·R80 교체 경로
- Controller 설치·유지보수·복구
- Writer 실행·설치
- SQLite 읽기·쓰기와 D1 게시
- 원장·checkpoint 갱신
- Actions concurrency와 PR 통합

자원별로 다음을 한 줄로 기록한다.

`자원 / 변경 주체 / 실행 계정·호스트 / 기존 보호 / 충돌 사례 / 보호 공백 / 처리`

처리는 `재사용·개선·신규·제외`로 분류한다.

**완료 기준:** 주요 충돌 경로와 최초 적용 대상이 정해진다. 조사 범위를 늘리는 일을 구현의 선행조건으로 만들지 않는다.

### 2단계. 최소 공통 계약과 충돌표 확정

공통 계약에는 필요한 정보만 둔다.

- 실제 자원 식별값
- 작업·실행 식별값과 소유자
- 읽기·쓰기·설치·복구 효과
- 소유권 세대 또는 토큰
- 획득·갱신·해제 규칙
- 기대 버전·SHA·CAS
- 정상 대기·중단·복구 상태
- 기존 실행 원장 연결

경로 문자열만으로 자원을 구분하지 않는다. Windows 대소문자·junction·별칭이 같은 실제 대상을 가리키는지 확인한다.

여러 자원을 함께 사용하는 작업은 획득 순서를 고정하거나 일부 획득 후 실패 시 되돌리는 방식으로 교착을 방지한다. 기존 잠금과 새 잠금을 중첩해 무한 대기시키지 않는다.

**완료 기준:** 어떤 조합이 병렬 실행되고 어떤 조합만 대기하는지 시험 가능한 표로 정의된다.

### 3단계. R54 한 경로에서 공통화 실증

R54 기존 구현을 출발점으로 가장 작은 보호 공백 하나를 개선한다.

- 기존 획득·해제·소유권 검증 재사용
- 기능 전용 경로와 공통 로직 분리
- 실행 소스와 교체 작업의 실제 연결 확인
- 동일 자원 경합과 독립 자원 병렬 실행 확인
- 실패·중간 종료 후 기존 원본 보존 확인

공통 모듈을 만들었다면 기존 구현을 그대로 남긴 채 이중 잠금을 추가하지 않는다. 기존 호출부를 연결하거나 호환 어댑터를 사용한다.

**완료 기준:** 첫 실제 연결 경로에서 보호 효과와 병렬 실행이 입증된다.

### 4단계. GitHub·Actions 통합 충돌 개선

기존 설정 중 실제 문제를 일으키는 부분만 수정한다.

- 소스 시험과 운영 변경의 concurrency 구분
- 자원과 무관한 전역 직렬화 제거
- 운영 변경 중 자동 취소 위험 조정
- 대기 원인·소유 작업·실행 단계 표시
- 동일 요청의 중복 실행 방지
- 변경된 PR HEAD에 대한 기존 검증 재사용 범위 명확화

두 저장소가 같은 운영 자원을 변경한다면 저장소별 대기열 설정만으로 충돌이 해결됐다고 가정하지 않는다. 실제 운영 진입점의 공통 보호를 확인한다.

Merge Queue는 지원·권한·기존 CI 호환성을 확인한 뒤 효과가 있을 때만 적용한다. 지원되지 않아도 전체 작업을 중단하지 않는다.

**완료 기준:** 같은 자원은 필요한 순서로 처리되고, 무관한 CI와 작업은 병렬로 진행한다.

### 5단계. Controller·Writer 기존 보호 연결

새 설치기나 복구기를 만들지 않고 기존 계약에 공통 자원 식별과 상태 연결을 적용한다.

필수 검증:

- 실제 실행 버전과 설치 대상 구분
- 변경 직전 소유권·원본 CAS 확인
- 여러 파일의 부분 교체 방지
- 승인된 백업과 실패 복구
- 복구 중 재설치·중복 실행 방지
- 기존 정상 프로세스 보존
- 접수 중지 시 backlog 회수
- 실패 후 최종 결과와 복구 상태 기록

기존 버전이 정상이라면 불필요한 파일 복사나 재시작을 하지 않는다. 정상 Runtime 검증에 설치 직전의 Idle 조건을 무조건 재사용하지 않는다.

**완료 기준:** 설치·실행·복구가 같은 실제 자원 경계에서 연결되고 기존 승인·보호 기능이 유지된다.

### 6단계. 경합·중단·병렬 처리 시험

격리 환경에서 실제 별도 프로세스를 사용해 검증한다. 단순 순차 fixture로 동시 실행을 입증하지 않는다.

| 시험 | 합격 기준 |
| --- | --- |
| 같은 자원 동시 변경 | 한 소유자만 변경 가능 |
| 독립 자원 작업 | 정상 병렬 실행 |
| 실행 중 소스 교체 | 혼합 버전 실행 방지 |
| 소유권·토큰 변조 | 변경·해제 거부 |
| 여러 자원 획득 실패 | 부분 잠금 정리·교착 없음 |
| 프로세스 중간 종료 | 원본·원장·복구 근거 보존 |
| 오래된 소유자 재개 | 새 소유자의 자원을 변경하지 못함 |
| 부분 설치 실패 | 검증된 원본 보존·정규 복구 |
| 별칭 경로 접근 | 동일 실제 자원으로 판정 |
| 저장소 간 운영 변경 | 같은 자원의 충돌 방지 |
| SQLite·D1 동시 작업 | 기존 일관성·CAS 계약 유지 |
| 취소·timeout·결과 누락 | 중복 효과 없이 상태 회수 |

시험 실패를 PASS로 바꾸기 위해 assertion이나 기대 보호 수준을 낮추지 않는다.

**완료 기준:** 변경 범위의 필수 시험이 모두 통과하고 미해결 항목의 영향 범위가 명확하다.

### 7단계. 단계적 운영 적용·효과 확인

첫 검증 경로부터 적용하고, 성공한 패턴을 다음 경로로 확장한다. 전체 시스템을 한 번에 교체하지 않는다.

운영 변경 전 정상본·설정·복구 경로를 확보한다. 실제 적용은 기존 승인 범위와 정규 절차를 따른다.

각 경로에서 다음을 확인한다.

- 동일 자원 충돌 처리
- 독립 작업의 병렬 실행
- 작업 대기 원인의 식별
- 완료·실패·복구 영수증
- 기존 기능·설정·데이터 보존
- 관찰된 대기시간과 전체 처리시간

**완료 기준:** 주요 공유 자원에 실제 적용됐고 보호 효과와 정상 작업 진행이 함께 확인된다.

## 5. 재발 방지 운영 규칙

1. 새 변경 경로를 추가하면 기존 자원 보호에 연결한다. 새 잠금을 기본으로 만들지 않는다.
2. 잠금 대기는 소유 작업과 대기 자원을 표시한다.
3. 동일 원인으로 실패한 실행을 새 요청 ID만 바꿔 반복하지 않는다.
4. 복구 시 원본 원장과 실패 증거를 보존한다.
5. 자동 취소·시간 초과가 실제 작업 중단을 의미하는지 구분한다.
6. 기존 정상 실행을 전체 복구의 불필요한 선행조건으로 중단하지 않는다.
7. 공통 보호 변경은 본체·PC 제어 담당이 같은 계약 버전을 확인한다.
8. 새 승인 Gate·상주 감시기·예약을 기본 산출물로 추가하지 않는다.

## 6. 효과 측정과 진행률

첨부 지시서의 비중은 관리상 진행률로 사용하되, 조사·설계 완료를 운영 기능 완료로 표현하지 않는다.

| 단계 | 비중 |
| --- | --- |
| 현황·보호 공백 확인 | 15% |
| 공통 계약·충돌표 | 15% |
| R54 재사용 실증 | 15% |
| GitHub·Actions 개선 | 15% |
| Controller·Writer 연결 | 15% |
| 경합·회귀시험 | 15% |
| 실제 운영 효과 확인 | 10% |

별도로 **운영 적용 대상 수 / 검증 완료 대상 수 / 미적용 대상 수**를 기록한다.

충돌·무결성 손상·비소유자 해제·불필요한 차단 0건은 관찰 범위의 목표다. 미래 사고 0건을 보장하는 수치로 보고하지 않는다.

대기시간 증가 10% 이내 목표는 같은 작업량·환경의 기준값이 있을 때 비교한다. 기준값이 없으면 먼저 측정하며 개선 수치를 추정하지 않는다.

## 7. 완료 판정과 롤백

다음 조건을 모두 만족해야 완료다.

- 주요 공유 자원의 변경 경로와 보호 계약 확인
- 기존 잠금 중복과 실제 보호 공백 처리
- 동일 자원 충돌 방지 실증
- 독립 작업 병렬 실행 실증
- 중간 종료·부분 실패·복구 시험 통과
- Controller·Writer 정상 기능 보존
- 실제 운영 적용과 사후검증 완료
- 관련 Issue·PR·운영 증거 연결

보호 기능 도입으로 정상 작업이 장기 차단되거나 처리 지연이 증가하면 해당 변경을 개선하거나 정규 절차로 롤백한다. 작업 중인 lease를 삭제하거나 기존 데이터·checkpoint를 초기화하는 방식은 사용하지 않는다.

## 8. 첫 실행

**첫 작업은 주요 실행 진입점의 보호 현황을 좁게 확인하고, R54에서 재현 가능한 충돌 한 건을 선정하는 것이다.**

그다음 기존 보호를 연결하는 최소 변경 → 격리 경합시험 → 독립 작업 병렬시험 → 승인된 실제 적용 순서로 진행한다.

대형사 기술 전수조사·Merge Queue 도입·전 시스템 추상화를 첫 개선의 선행조건으로 만들지 않는다.
