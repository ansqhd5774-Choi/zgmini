D05는 새로운 산식이나 수집기를 만드는 작업이 아니다. 기존 승인된 계산 결과와 저장·공개 경로를 재사용하고, 실제 누락·불일치가 확인된 연결만 수정한다.

PC 제어 문제가 발견되면 정확한 요청과 증거를 공통 담당자에게 인계한다. D05 담당자가 보조 저장소에서 Controller 개선 업무로 확장하지 않는다.

## 2. 현재 상태와 시작점

전용 브랜치에는 다음 구현이 존재한다.

- 최종 계산 출력 사건 생성과 일별 선택
- 시장 저장 결과 readback
- 업종 저장 결과 readback
- 테마 계산 후보 readback
- Writer 연결 및 관련 시험 파일

**코드 존재는 운영 완료 증거가 아니다.**

첨부 보고의 다음 실적은 기존 증거를 연결해 재사용한다.

| 대상 | 승계할 결과 | 남은 확인 |
| --- | --- | --- |
| 업종 | #3128의 특정 계산 사건 로컬·D1·API 일치 | 이후 최신 사건·화면·이력 |
| 테마 | #3215의 로컬 계산·저장 결과 | 동일 사건의 D1·API·화면 |
| 시장 | 27개 논리 ID 매핑, 공통 13개와 별도 14개 구분 | 실제 출력·저장·공개 연결 |

기존 `86%`는 이전 보고치로만 보존한다. 이번 계획의 검증된 진행률로 재사용하지 않는다.

**현재 위치: 아래 1단계부터 시작한다.** 이번 확인으로 새로운 운영 완료 항목을 추가하지 않는다.

## 3. 실행계획 — 7단계

### 1단계. 실제 대상과 최초 미완료 연결 확정

기존 매핑과 실행 영수증을 사용해 대상별 한 줄 원장을 만든다.

기록할 내용:

`ID / 출력 종류 / 계산 소스 / 로컬 저장 / 공개 키 / API / 화면 / 마지막 유효 증거 / 다음 행동`

- 시장 27개는 점수·비율·별도 기능을 구분한다.
- 업종은 현재 승인된 등록 목록을 사용한다.
- 테마는 운영 등록 목록에서 공개 승인 대상을 읽는다.
- 미개발 테마를 임의로 포함하지 않는다.
- 제거된 이란 기능·예약은 복원하지 않는다. D27은 최신 운영 결정에 따라 제외 또는 현행 대상 여부를 명시한다.

**완료 기준:** 각 대상의 경로와 최초 미완료 지점이 특정된다. 존재하는 매핑을 새로 설계하지 않는다.

### 2단계. 계산 사건과 저장시각 계약 확인

기존 Writer와 최종 출력 모듈을 대조한다.

특히 시장 readback은 `stored_at`을 계산시각으로 사용하므로, 실제 Writer 호출에서 해당 값이 계산 완료 시각과 연결되는지 확인한다.

- 동일 시각이라는 실행 계약·영수증이 있으면 재사용한다.
- 단순 저장시각만 확인되면 계산시각 검증으로 확대하지 않는다.
- 기존 정상 데이터에 새 필드를 강제하거나 계산시각을 임의 생성하지 않는다.
- domains 배열 순서보다 ID를 기준으로 비교한다.
- 결측 점수와 숫자 0을 구분한다.
- 사건 ID가 없는 공개 데이터는 기존 공개 projection의 대응 필드로 비교한다.

**완료 기준:** 계산 사건을 입증하는 자료와 단순 저장 스냅샷을 구분하고, 현재 정상 경로를 사용할 수 있다. 결함이 확인된 연결만 최소 수정한다.

### 3단계. 시장·업종·테마 로컬 결과 확인

같은 자료를 여러 진단으로 반복 조회하지 않고 기존 읽기 경로와 영수증을 재사용한다.

| 대상 | 확인 내용 |
| --- | --- |
| 시장 공통 13개 | overall·12개 영역의 실제 값, 관측일, 계산 사건, 저장 결과 |
| 시장 별도 14개 | 각 기능 고유 출력 계약과 실제 저장 결과 |
| 업종 | 등록 대상별 최신 유효 계산 사건 |
| 테마 | 공개 승인 대상별 확정·잠정 사건과 저장 결과 |

준비되지 않은 개별 항목 때문에 나머지 대상의 검증을 중단하지 않는다.

**완료 기준:** 각 대상이 정상·결측·지연·불일치·미검증 중 하나로 근거와 함께 분류된다. 결함으로 누락된 결과는 기존 승인 경로에서 복구한다.

### 4단계. 로컬 → D1 → API 연결 완성

같은 계산 사건을 세 위치에서 비교한다.

- ID·점수 또는 비율
- 관측일
- 산식 버전
- 확정·잠정 구분
- 기존 사건 식별값 또는 검증된 대응 필드

실패 위치에 따라 작업을 한정한다.

| 확인된 문제 | 조치 |
| --- | --- |
| 로컬 정상·D1 누락 | 기존 게시기의 해당 키와 실행 실패 수정 |
| D1 정상·API 불일치 | Reader·키·캐시·버전·날짜 연결 수정 |
| 로컬 결과 없음 | 기존 계산·저장 경로의 최초 실패 수정 |
| 정상적인 자료 대기 | 마지막 유효값과 지연 상태 보존 |

게시 결과가 불명확하면 D1을 먼저 재조회한다. 무조건 재게시하지 않는다.

**완료 기준:** 대상별 공개 결과가 검증된 로컬 사건과 일치하거나, 정상적인 결측·지연 사유를 정확히 반환한다.

### 5단계. 날짜별 이력과 차트 연결

실제로 저장된 최종 점수 이력을 사용한다.

- 관측일, 계산일, 저장일을 구분한다.
- 날짜별 마지막 실제 계산 사건 선택 규칙을 유지한다.
- 로컬·D1·API의 시작일·마지막 날짜·실제 점 수를 비교한다.
- 마지막 차트 점을 최신 유효 공개 사건과 연결한다.
- 과거 재계산 결과는 당시 실제 계산 기록과 구분한다.
- 결측 보간·0점 채우기·계산시각 소급 변경은 하지 않는다.

**완료 기준:** 존재하는 이력이 누락 없이 표시되고 실제 제공 기간이 정확하다.

**1년 기록이 없다는 이유로 기능 완성을 1년 동안 대기하지 않는다.** 확인된 기간을 제공하고 부족한 기간을 표시한다.

### 6단계. 실제 PC·모바일 화면 확인

PC 1440px와 모바일 390px에서 다음을 확인한다.

- 카드 값과 API 값
- 점수·비율·단위
- 날짜·확정·잠정·지연 표시
- 차트 마지막 점과 날짜별 연결
- 0·결측 구분
- 텍스트 잘림과 차트 오류

D04 등 데이터 연결 문제가 확인되면 기존 컴포넌트의 입력만 수정한다. 무관한 디자인 개편은 하지 않는다.

D05 데이터·연결 수정은 전용 브랜치에서 진행한다. 별도 UI 디자인 작업이 필요하면 UI 담당자 범위로 분리한다.

**완료 기준:** 실제 화면이 검증된 API 결과와 일치한다.

### 7단계. 필요한 변경 통합과 운영 완료

변경이 있는 경우에만 관련 시험·PR·운영 적용을 수행한다.

- PR 전체 diff에서 D05 변경만 확인한다.
- 기존 유효 시험은 재사용하고 영향받은 부분만 재검증한다.
- 웹 변경은 기존 Git 연동 배포 절차를 따른다.
- Writer 변경은 기존 승인된 운영 적용 경로를 따른다.
- 실제 저장·게시·API·화면 결과를 확인한다.
- 완료 조건을 충족한 Issue만 종결한다.

**완료 기준:** 기능별 운영 증거와 정확한 잔여 문제가 기록되고, 구현 완료와 운영 완료가 구분된다.

## 4. 공통 실행 문제 처리

PR #3239와 신규 A급 operation은 **필요한 관측 수단 중 하나**다. D05 전체의 필수 선행조건으로 고정하지 않는다.

기존 승인된 조회로 필요한 증거를 확보할 수 있으면 추가 Controller 설치 없이 진행한다.

공통 실행 경로가 실제로 막히면 다음만 인계한다.

1. 막힌 대상과 정확한 실행
2. 현재 설치·요청·오류 증거
3. 필요한 최소 공통 조치
4. 복구 후 반환받을 결과

해당 경로에 의존하지 않는 D1·API·소스·화면 작업은 계속한다. 새로운 Gate·예약·진단 체계를 만들지 않는다.

## 5. 최종 완료 기준

다음이 충족되면 D05 기능 완료로 판정한다.

- 승인된 대상 목록과 제외 대상이 명확하다.
- 실제 최종 계산값이 기존 저장 경로에 연결된다.
- 공개 대상의 로컬·D1·API 결과가 일치한다.
- 결측·지연이 정상 상태와 구분된다.
- 실제 이력과 차트가 연결된다.
- PC·모바일 화면이 공개 결과와 일치한다.
- 기존 산식·공급자 정책·원자료·과거 이력을 보존한다.

**모든 항목이 숫자를 반환해야 완료인 것은 아니다.** 정상적인 결측·자료 대기는 정확히 표시하되, 코드 결함으로 인한 누락을 정상 결측으로 종결하지 않는다.

## 6. 진행 기록

각 단계는 `미착수 / 진행 중 / 완료 / 해당 범위 차단`으로 관리한다. 단계 개수를 기능 완료율로 단순 환산하지 않는다.

보고는 다음만 남긴다.

- 작업 브랜치와 실제 커밋
- 이번 완료 단계와 운영 증거
- 시장·업종·테마별 검증 대상/완료/결함/정상 대기
- 현재 목표를 실제로 막는 문제
- 다음 직접 실행할 작업

**첫 실행은 1단계의 대상 원장 정리와 2단계의 시장 계산시각 계약 확인이다. 기존 결과가 정상이라면 즉시 D1·API 대조로 넘어간다.**
