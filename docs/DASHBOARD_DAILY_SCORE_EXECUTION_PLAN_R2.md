## 1. 목적·완료의 정확한 의미

### 1.1 사용자 최초 문제
대시보드에서 서로 다른 기능의 점수가 **산식에 필요한 신규 지표가 수집되면 갱신되는지**, 아니면 **별도 일·월·분기 산출 기간이 도래해야만 출력되는지** 일관되지 않게 보이는 문제를 해결한다. 화면의 60초 자동 GET을 계산 주기라고 설명해서는 안 된다.

### 1.2 1차 완료 목표 — 최신 현재 점수(A)
유효한 신규 원자료가 PC 로컬 저장소에 저장되고 기존 산식이 허용하는 입력 조건을 만족하면, **승인된 다음 실행 기회**에 해당 영향 산식만 재계산 → 로컬 결과 저장 → 승인 D1 key 게시/readback → 공개 API/UI 반영한다. 월·분기 입력이 존재한다는 이유만으로 전역 월말/분기말 대기를 강제하지 않는다. 단, 공통 완료월, 완료분기, 전체 READY, 잠정/확정 분리 등 개별 승인 Gate를 통과하지 않으면 신규 **확정** 점수를 게시하지 않는다. 일률적인 분 단위 실시간 SLA를 추정하지 않는다.

### 1.3 병행하되 독립적으로 완료할 목표 — 이력(B)
최신 점수/당일 잠정 계산/실제 계산 사건/일별 최종 스냅샷/월·분기 공식 확정/소급 재구성점을 서로 구분한다. 마지막 유효값 이월은 가능하나 신규 공식 관측으로 표시하지 않는다. 동일일 정정은 원본 기록을 보호하는 승인된 revision 방식이어야 하며, 과거 자료를 조용히 최신 빈티지 값으로 덮어쓰지 않는다. B의 미완료가 A의 독립 적용을 막지 않되, A를 적용하면서 기존 이력을 파괴해서는 안 된다.

### 1.4 표시 계약
카드의 현재값·소수점·상태·기준일, 차트의 마지막 실제 점·기준일·결측, 상세화면의 잠정/확정 상태를 **동일 공개 결과의 해당 의미**에 맞춰 표시한다. `0`은 유효 점수일 수 있으며 `null/missing/stale/PARTIAL/UNAVAILABLE`을 숫자 0으로 대체하지 않는다. `sourceStoredAt`은 공식 원관측일이 아니며, 화면 재조회 시각은 계산/게시시각이 아니다. 방문자 GET은 저장된 게시 결과만 읽는다.

## 3. 정상·결함·미연결 구분과 완료 판정

### 3.1 기능별 한 줄 운영 계약(27행)
기존 인벤토리의 D01–D27 각 행을 **재조사해서 새 ID를 만드는 대신** 활용하고 다음 컬럼을 증거가 존재하는 범위에서 채운다.

`auditId | 화면/route | 원자료 provider/series 및 observationDate | 실제 입력주기(일/T+1/주/월/분기/비정기) | 산식 READY/완결 Gate | 허용 이월 | 입력 checkpoint/signature | calculator/formulaVersion | local result key | 게시 D1 key | public API/필드 | UI 카드/차트 표시 일자 | 최종 계산/게시 사건 | 원담당 | 상태 및 정확한 근거`.

필드가 필요하지 않은 콘텐츠는 `N/A(사유)`, 조회 증거가 없는 항목은 `UNKNOWN(필요한 정확한 1건)`으로 기록한다. 기존 2026-11-10 관측 수치를 2026-11-16 현재값처럼 재사용하지 않는다. 같은 27행의 이미 확보한 근거를 반복 조회하지 않는다.

## 4. 실행 5단계·작업 단위·수락 기준

### 단계 1 — 기존 27개 갱신·출력 기준표 확정 (배점 15%)
**담당:** W06(공개 UI와 표시 계약), 기능 원담당(활성 계산 Gate/운영 사실).
1. R1의 D01–D27 ID·코드·route를 그대로 사용한다. D26/D27은 보조 콘텐츠로 표시한다.
2. 기존 API 11개, PC 원장 7건, 68개 인벤토리 및 이후 실제 승인 결과를 **재사용**하고 변경된 source/설정에 한해 관련 행만 갱신한다.
3. 각 행에 입력 발표·원관측일, READY/잠정/확정 Gate, 입력 변경 판정기, 현재/차트 의미, 게시 경로, 최종 상태를 붙인다.
4. 27개를 NORMAL / DEFECT_UI / DEFECT_CALC_PUBLISH / NOT_CONNECTED / EXPECTED_WAIT / UNKNOWN / DEFERRED 중 하나로 분류한다. 결함 수·수정 대상 수를 공개한다.
**PASS:** 27/27 행의 근거·상태·담당·다음 행동 존재, 근거 부족이면 UNKNOWN으로 명시. 27개 전부의 새로운 PC→D1 종단 영수증을 1단계의 필수 조건으로 만들지 않는다.

### 단계 2 — 수정할 결함 재현 및 최소 범위 확정 (배점 15%)
**담당:** 각 오류 소유자, W06은 UI/소비자 계약.
1. D05의 `worker/projection-checkpoint-r52.mjs:readCoreCheckpoint`가 `current.stored_at`을 `core:<timestamp>`로 사용하는 지점과 `scripts/pc-writer/run-local.mjs`의 저장/재게시 사건을 분리하여 재현한다.
2. **신규 원자료 없음+current만 재저장**, **실제 신규 원자료+승인 Gate 충족**, **원자료 신규이나 Gate 미충족**의 세 사례를 입력 signature/원관측일과 비교한다.
3. D15/D08/D11의 서로 다른 발표주기와 확정/잠정 제한이 새 입력 반영 실패인지 정상 대기인지 분류한다.
4. 실제 잘못된 재계산/게시 사례가 증명되지 않으면 `DESIGN_RISK`로 남기고 정상 코드를 추측으로 교체하지 않는다.
5. 확인된 결함마다 원인 파일·변경 최소 줄/필드·기존 호환성·사용될 기존 Runner/Writer 경로·테스트 이름·원담당을 확정한다.
**PASS:** 수정 대상 **각 건**에 재현 입력/기대/실제/원인/영향/담당/승인 범위 기록. 소스 위험을 실제 운영 실패라고 과장하지 않음.

### 단계 3 — 실제 결함 수정·승인 경로 적용 (배점 40%)
**담당:** W06(표시 코드), 기존 해당 기능 원담당(Collector·Calculator·Writer), 공유 Writer 장애일 때 공통 Owner.
1. UI 결함은 **해당 카드/차트/상세 소비자만** 수정한다. 기존 디자인·승인된 점수/소수점·색상·산식·기간을 임의 변경하지 않는다.
2. 입력 감지 오류가 재현된 기능은 사용 입력의 관측/버전/checkpoint 또는 허용된 인과 signature로 변경 여부를 판정한다. 단순 `current.stored_at` 변경, TTL/시장 경계/공식 정정 등 정당한 실행 사유를 각각 보존한다.
3. 기존 `local-cycle` / `progressive-publication` / Writer를 재사용한다. 실제 신규 입력으로 영향받는 계산기만 실행→로컬 결과/원장 기록→승인 D1 게시/readback→API 화면 반영한다.
4. 당일 다회 계산은 실제 사건을 남기되 일별 최종 스냅샷과 혼합하지 않는다. 과거 확정점은 revision 계약 없이 덮어쓰지 않는다.
5. 기존 DB·D1 field/key·TTL·sourceVersion 의미·운영 source·수집 주기·DNS/배포 경로를 바꿔야 한다면 **정확한 변경 명세·위험·호환성·원본 보호**를 작성하고 해당 범위의 사용자 승인을 받은 후 수행한다. 승인 전에는 분리 가능한 UI/소스·관련 테스트만 진행한다.
6. 변경 최소 파일 테스트→원격 SHA 확인→해당 승인된 PC 설치 또는 정규 Cloudflare Git Integration→로컬 결과/D1 readback→공개 API/UI 확인. PR·CI만으로 운영 완료 주장 금지.
**PASS:** 확인된 수정 대상별 개발·운영 증거 구분, 운영 기능에 대해 정확한 버전/결과까지 확인. 영향 없는 27개 항목은 재설치 요구 금지.

### 단계 4 — 혼합주기·회귀 시뮬레이션 (배점 15%)
**담당:** 기능 원담당(산식), W06(카드·차트).
다음 사례에 **EXPECTED/ACTUAL/PASS 또는 FAIL + 입력 signature/원관측일** 기록:
1. 일별(T+1)만 바뀌고 월·분기 입력은 기존 유효값 이월.
2. 2일에 월간 5개 중 한 지표의 신규 발표·저장: Gate 허용 시 재계산.
3. 분기 2개 중 일부만 발표: 미완성 분기의 신규 확정점 금지.
4. 같은 날짜에 유효 입력 변경 2회: 이벤트 이력 유지, 마지막 공개값 최신.
5. 완전히 동일한 checkpoint 재수집/현재 snapshot 재저장: 신규 공식 관측으로 표시 금지.
6. 공식 과거 정정: 원본 불변 + 승인 revision/supersedes 절차; 임의 backfill 금지.
7. 공급자 실패/결측/TTL 경과/D1 게시 실패: 0과 null 분리, 마지막 유효값 유지와 상태 정확성.
8. KST/미국 거래일·휴장/DST 경계: 관측/계산/게시/UI 날짜 분리.
**PASS:** 변경 영향 사례의 관련 회귀 모두 PASS, 기존 READY·완성월/분기 보호, 정확한 실패 격리. 테스트용 자료를 공개 저장소/Production 원자료에 주입하지 않음.

### 단계 5 — 실제 운영 반영·공개 출력 종단 확인 (배점 15%)
**담당:** 해당 기능 원담당(PC/D1), W06(API↔홈 화면).
1. 변경된 기능에서 **실제 신규 유효 원자료 사건 1개 이상**의 `observationDate/releasedAt → local sourceStoredAt/checkpoint → calculatedAt/input signature → local result → publishedAt/D1 readback/version → API/UI`를 추적한다.
2. D05·D15·D08·D11 중 **변경된 대표 경로**와 그 영향 범위에 대해서만 필요한 현장 검사를 수행한다. 정상인 모든 콘텐츠에 신규 입력·재설치를 강제하지 않는다.
3. 카드의 현재값·계산일·원관측일·잠정/확정과 차트 마지막 점이 실제 공개 계약과 동일한지 PC/모바일에서 확인한다. 발표 지연 또는 원자료가 없는 기능은 정상 대기/미확인으로 분리한다.
4. 기존 게시 기능 중 실제 미완료는 별도 남겨두고, **수정 가능 범위의 최종 완료 여부**를 개별 정리한다. 사후 예약 자연검증은 별도 후속이며 종단 작업 완료의 임의 선행조건으로 추가하지 않는다.
**PASS:** 변경 대상별 last valid, 신규 관측, 계산, D1, API/UI 연계 및 배포 SHA/PC 설치 SHA를 서로 구분한 증거. 수정 없던 정상 기능은 이전 유효 증거 재사용.

## 5. 책임·승인·병렬 처리

| 업무 | 실행 Owner | W06 수행 범위 |
|---|---|---|
| 27개 출력계약 분류, 홈/차트/date/결측 정합 | W06 | **직접 실행** |
| 원지표 수집·계산/READY·관측주기 확정 | 기능별 원담당 W01~W04 등 | 해당 계약을 인용하고 증거 수신/대조 |
| 공통 Writer/Controller 구조적 장애 | 공통 PC Owner | 문제 재현·영향 경계·인계, 무단 설치 금지 |
| D1 게시/소스↔API 실연결 | 기존 기능/게시 Owner 및 W05 | API/UI readback 검증 협업 |
| 섹터 S11·테마 T30의 등록·원자료·권리·계산 | 기능별 기존 담당 | 준비된 공개값의 화면 의미 검증만 |
| 실제 운영 승인 범위 밖 DB/API/schema/TTL/산식/예약/DNS 변경 | 사용자 명시 승인 후 정규 Owner | 변경 필요성·최소 영향만 문서화 |

단계 1·2의 읽기/소스 대조와 단계 4의 모의실험은 독립 병행 가능하다. 같은 파일/DB/D1/Writer에 중복 쓰기하지 않고 승인된 lease에 따른다. 새로운 Controller 재설치·전 Runner 유휴·공용 전체 검사를 기본 Gate로 만들지 않는다. 정상 서비스의 다른 기능은 기다리게 하지 않는다.

## 6. 진행률과 상태 집계 (구형 0/7 오류 방지)

**전체 R2 적용 진행률** = `0.15×(S1 증거완료 단위/계획단위) + 0.15×(S2 증거완료 단위/계획단위) + 0.40×(S3 적용완료 수정단위/확정 수정단위) + 0.15×(S4 시나리오 PASS/실제 대상 시나리오) + 0.15×(S5 운영검증 완료 수정단위/운영검증 대상)` × 100%.

- S1: 27개 계약 행 중 근거·상태·담당·다음 행동 4필드 충족 행을 분자로 한다. **기존 68/68 ID 식별만은 S1 완료로 환산하지 않는다**.
- S2: 단계 1에서 발견한 수정 후보 중 재현·정상 대기 판별·최소 영향·Owner가 확인된 항목을 분자로 한다. 후보가 없는 경우에는 27개 NORMAL/EXPECTED_WAIT 분류의 실제 근거를 판정하고 무분모를 100%로 자동 처리하지 않는다.
- S3: 변경이 필요하다고 확정된 수정 단위 중 승인된 실제 적용을 완료한 수. 원래부터 NORMAL인 콘텐츠는 '수정 완료' 분자에 넣지 않는다.
- S4: 해당 변경·산식 Gate에 영향을 주는 시나리오 테스트의 실제 PASS 수. 시뮬레이션으로 68개 전체 운영을 PASS 처리하지 않는다.
- S5: 수정 대상 중 PC 설치가 필요한 경우 PC/D1/API/UI, UI만 변경된 경우 정규 배포/API/UI 증거까지 확인한 수. 서로 다른 완료 조건은 사전에 해당 수정 단위별로 고정한다.
- **분모가 미확정인 단계는 0%로 고정하거나 100%로 가정하지 않고 `미산정`으로 보고**한다. 그 대신 이미 확인된 하위 실적은 각각 `n/N`으로 표현한다.
- **별도 집계:** (1) A의 27개 상태 분포, (2) A 수정대상 PASS n/N, (3) B S01–S11 독립 완료율, (4) C T01–T30 카탈로그/등록/게시 각각의 분모, (5) 개발·PC·D1·API/UI 실제 완료 구분.
- 당시의 **7단계 완료 0/7**은 2026-11-10 R1 기록에 대한 판정이다. R2 진행률로 변환하지 않는다. 기존 68/68 식별, 11/11 API 읽기, PC 원장 7건, 3파일 해시 PASS를 보존해 중복 조사하지 않는다.
