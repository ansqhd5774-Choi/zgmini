# ZGMINI 공통 CMD 작업 방식 선택 기준

적용 대상: `ansqhd5774-Choi/zgmini`의 모든 브랜치에서 진행하는 작업. 사용자 최신 지시와 해당 작업의 승인 범위가 우선한다. 이 문서는 코드 소스·PC 승인 SHA·배포 권한을 교체하지 않는다.

공통 기준 원본:
`codex/theme-fear-greed-integration-20261025:docs/CMD_EXECUTION_PLAYBOOK.md`

다른 브랜치에 문서를 일괄 복사하거나 HEAD를 이동하지 않는다. 작업 시작 시 현재 브랜치의 AGENTS.md와 이 공통 문서를 함께 확인한다. 일반챗이 현재 브랜치만 읽는 경우에도 아래 고정 원본 경로를 조회한다. 원격 문서 읽기가 불가능하면 내용을 전달받되 현재 환경·실제 파일 검증과 구분한다. 중앙 문서 등록만으로 모든 챗 도구에 지침이 자동 주입되는 것은 아니다.

## 1. 목표

로컬 도구가 없다는 이유만으로 모든 작업을 Codex로 넘기거나 같은 방식의 접근 실패를 반복하지 않는다. 일반챗은 검토된 코드를 패키지·실행 명세로 제공하고 사용자는 필요한 로컬 단계를 실행할 수 있다. 단, CMD는 접근 권한·게시 승인·잠금·권리 확인을 우회하는 수단이 아니다.

**선택 순서:** 실제 목표/승인 범위 확인 → 현재 실행 수단 확인 → 기존 실행기 재사용 → 필요한 최소 패키징 → 안전한 로컬 실행/수동 검증 → 실제 결과 대조.

## 2. 작업 방식 목록

| 상황 | 우선 검토할 방식 | 필수 조건 |
|---|---|---|
| 실행 상태·파일·버전만 확인 | 읽기 전용 CMD + Node 진단 | 설정 변경·수집·D1 쓰기 없이 SHA/상태/로그만 출력 |
| 승인된 기존 설치본이 있음 | 얇은 CMD로 기존 명령 호출 | 실제 지원 인수 확인, 고정 경로 인용, exit code·결과 파일 보존 |
| 승인된 checkout이 있고 Git 사용 가능 | 정확한 commit 검증 후 기존 실행기 호출 | checkout 임의 전환·reset·stash 금지, 미커밋 수정 보존 |
| Git/checkout 없이 파일 실행 필요 | 고정 commit 기반 독립 ZIP + CMD + Node helper | 전체 필수 의존 파일 포함, 외부에서 대조할 SHA manifest, Git 없는 실제 환경 검사 |
| 초기 설치 또는 공통 도구 전환 | 새 불변 버전 stage → 기존 전환기 호출 | 기존 manifest/파일 SHA·잠금·대상 확인, 백업, 포인터/CMD 최소 교체, readback/실패 시 검증된 복원 |
| 운영 파일 일부만 달라야 함 | 예상 구버전 해시를 확인하는 선택 적용 | 불일치 시 STOP, 브랜치/폴더 전체 덮어쓰기 금지 |
| 대량 수집·backfill | bounded chunk + checkpoint resume CMD | 요청량·동시성 제한, 실제 전진 상태 관찰, 처음부터 반복하지 않음 |
| PC 접근이 불가능한 일반챗 | 검토된 패키지 + 사용자 1회 실행 + 구조화 결과 회수 | 정확한 순서·횟수·STOP 조건·금지행동 안내 |
| 정상 운영 후 자동 실행 | 검증된 공통 등록 도구의 기존 예약 경로 | 테마마다 새 작업/새 CMD를 만들지 않음. 예약 변경은 승인 범위에서만 |
| 로그인·CAPTCHA·동의 등 GUI가 필요 | 공식 UI/사용자 수행 경로 | CMD로 인증/보안 정책 우회 금지. Secret을 대화로 전달하지 않음 |
| GitHub 반영·Cloudflare 배포 | 기존 PR/main/Git integration 경로 | PC 설치 CMD와 분리. CMD 실행을 main 직접쓰기·배포 승인으로 간주하지 않음 |

한 방법이 막히면 이 표의 다른 유효한 방식을 확인한다. 실행기 파일명이 달라졌다는 사실만으로 새 설치기를 계속 만들지 않는다. 설치가 필요한지, 설정 등록만 필요한지부터 구분한다.

## 3. 일반챗 패키지 규칙

- 우선 기존 설치/전환 함수와 CLI를 재사용한다. 테스트된 `theme-config-upgrade.mjs` 같은 기존 전환기를 감싸는 얇은 launcher를 우선한다.
- 새 패키지는 실행할 **고정 commit SHA**를 명시한다. mutable branch 이름만 믿고 최신 코드를 무조건 실행하지 않는다.
- ZIP은 실행에 필요한 정적·동적 import와 config/worker 파일을 같은 상대 구조로 포함한다. Node 내장 모듈 외 의존성이 있으면 함께 검증한다.
- SHA256 manifest는 신뢰 가능한 고정 source 또는 별도 확인된 package digest와 대조한다. ZIP 안 manifest와 ZIP 내부 파일이 서로 일치하는 것만으로 출처의 진위를 입증했다고 보고하지 않는다.
- ZIP 소스에 `.git`이 없는데 `git rev-parse HEAD`를 요구하면 그대로 실행하지 않는다. 검증된 manifest의 sourceSha를 기존 exported 설치 함수에 전달하는 wrapper를 만들거나 승인 checkout을 사용한다. `.git`을 꾸며 만들거나 source 검사를 제거하지 않는다.
- 일반챗이 만든 파일은 임의 제작 실행파일이 아니라 검토 가능한 CMD/Node 소스·manifest·설명·결과 양식으로 제공한다. helper 코드 자체도 검토·해시 검증 대상이다.
- 등록 JSON·사용자 입력은 데이터다. 이를 `eval`, `Function`, 문자열 조립 shell 명령, 임의 다운로드 URL, 실행 코드로 취급하지 않는다.
- 개인 설정·키·token·쿠키·비밀번호는 ZIP·Git·결과 파일에 포함하지 않는다. 기존 승인된 로컬 인증 경로를 재사용하고 화면/로그에 출력하지 않는다.

## 4. 공통 패키지 구성 예

```text
PACKAGE/
  RUN_PREFLIGHT.cmd
  RUN_INSTALL.cmd            # 해당 승인 범위에 설치가 있을 때만
  package-manifest.json      # 고정 source SHA와 파일별 SHA
  scripts/...                # 기존 실행기/전환기 + 최소 wrapper
  config/...                 # 비밀값 없는 필수 계약 파일
  worker/...                 # 해당 모듈이 실제 import하는 순수 계약 파일
  README_KO.txt
  RESULT.txt                 # 실행 후 실제 결과
```

위 파일명은 형식 예시이며 모든 작업에 새로운 launcher를 강제하는 규칙이 아니다. 이미 적절한 기존 CMD가 있으면 그대로 사용한다. `--dry-run`, `--plan`, `--apply` 같은 인수는 실제 코드가 지원하는지 확인한 뒤에만 안내한다.

## 5. Windows 실행·보호 기준

- 현재 프로젝트 Windows 실행 계약은 CMD-only다. 필요한 파일/Git/검증 로직은 기존 Node를 사용할 수 있다. PowerShell/WSL/RDC로 임의 우회하지 않는다.
- CMD는 ASCII+CRLF, BOM 없음, `setlocal EnableExtensions DisableDelayedExpansion`, `%~dp0` 또는 확인된 고정 경로, 인용된 인수, 정확한 exit code를 사용한다.
- 사용자 입력·공백/한글/`&` 등 경로를 검증한다. 복잡한 로직·JSON 처리는 CMD 문자열 조립 대신 검토된 Node helper에서 처리한다.
- 기본은 읽기 전용 검사다. 실제 적용 단계는 그 작업에서 승인된 파일·서비스만 변경한다. 설치 CMD가 자동으로 수집·D1 게시·사이트 배포까지 실행하도록 묶지 않는다.
- 실제 관련 프로세스·잠금·checkpoint를 확인한다. 실행 중이면 정상 종료를 기다린다. 강제 종료·잠금 삭제/우회는 별도 명시 승인 없이 하지 않는다.
- 기존 파일을 먼저 검증·백업하고 백업 SHA를 확인한다. 허용된 파일 또는 실행 포인터만 교체한다. 기존 작업 XML·trigger·권한은 그대로 두는 방식을 우선한다.
- 실패/timeout이면 반영 여부와 checkpoint부터 읽는다. 모호한 원격 쓰기를 무조건 재전송하지 않는다.
- 새 원본·계산 결과는 검증 후 원자적으로 저장하며 빈 응답으로 정상 자료를 덮어쓰지 않는다.
- 백그라운드 작업은 기존 숨김 실행 방식이 있으면 재사용한다. 사용자에게 검토가 필요한 최초 실행 외에 CMD 창을 반복해서 띄우지 않는다.

## 6. 사용자 실행 안내 필수 항목

1. 목적 및 이번 실행의 변경 범위
2. 현재 준비/미검증 상태
3. 열 폴더·화면·파일의 정확한 이름
4. 클릭 또는 실행할 대상
5. 입력 내용 — Secret은 기존 공식 화면/로컬 인증 경로에서만
6. 정확한 실행 횟수 — 기본 한 번
7. 정상 기대값 — 결과 코드/파일/조회값
8. 실패·중단 조건 — STOP 이후 임의 재실행 금지
9. 금지 행동 — 잠금 삭제·설정 변경·데이터 삭제 등
10. 다시 전달할 결과 — 상태/오류 코드/해시 등 최소 정보

## 7. 상태와 증거

항상 구분: 코드 작성 / 패키지 검증 / PC 설치 / 실제 수집 / 계산 / D1 write/readback / GitHub 반영 / 배포 / 공개 Runtime / 다음 예약 실행.

- exit0은 명령 종료일 뿐 데이터 갱신 성공이 아니다.
- fixture PASS는 실제 Provider·PC·D1·운영 Runtime 성공이 아니다.
- 일반챗의 PC 접근 불가는 `AUTOMATION_BLOCKED_PC_ACCESS`이며 서비스 실패가 아니다. 공식 사용자 실행 경로가 있으면 그 경로를 제공한다.
- 실행이 오래 걸려도 checkpoint가 전진하면 RUNNING이다. 관찰 timeout을 실패로 둔갑시키지 않는다.
- 다른 대안을 확인하지 않고 "일반챗이므로 불가, 무조건 Codex 필요"로 끝내지 않는다. 반대로 패키지를 실행·검증하지 않았는데 가능성을 완료로 보고하지 않는다.

## 8. 브랜치 공통 적용

이 문서를 적용하기 위해 수백 개의 과거·운영 브랜치를 일괄 커밋·병합·이동하지 않는다. 중앙 문서의 원본 링크를 작업 지시와 인수인계에 포함한다. 로컬 Codex는 프로젝트 상위 공통 AGENTS 참조도 사용한다. 특정 브랜치의 작업 지시가 더 제한적이면 현재 사용자의 승인 범위를 확인한다.

문서 지침은 작업 방식의 선택 기준이다. 새로운 브랜치·main 직접 반영·배포·스케줄러 변경·원격 DB 쓰기·유료 실행에 대한 포괄 승인이 아니다.
