## 1. 올바른 목표와 완료 기준

**목표:** 기존 승인 산식과 공개 데이터 계약을 유지하면서, 대시보드 점수의 카드·상세·차트 및 PC/모바일 출력이 각자의 승인된 표현 규칙에 맞게 일관되도록 정리한다.

- 먼저 실제 출력 대상과 페이지·컴포넌트·사용 중인 데이터/API/기존 표시 변환을 확인한다. `27+11+30=68`은 다른 일별 이력 과제의 **논리 대상 목록**이며, 곧바로 UI 수정 완료율 분모가 아니다.
- 점수 값/소수점/단위/상태/색상/라벨/날짜/차트 끝점/24시간 변화 화살표를 **기존 승인 규칙대로** 대조한다. 모든 콘텐츠에 임의로 같은 반올림·색상·상태 또는 원점수 표시를 강제하지 않는다.
- 서로 다른 raw 점수와 승인된 화면 민감도 변환은 구분한다. 실제 원자료가 갱신되지 않았다는 사유로 UI 출력 정합 작업 전체를 중단하지 않는다.
- 결측·부분·stale·잠정·확정을 최신 READY와 혼동해 보이게 하지 않는다. 차트·카드에서 사용한 관측일·계산일·게시일의 **현재 공개 계약**을 확인해 올바르게 표시한다.
- UI 작업이 끝났다는 판정에는 범위별 실제 화면/API 대조·PC/모바일 회귀 검사, 승인된 배포 시에는 정확한 GitHub/Cloudflare/Production 증거가 필요하다.
- 기존 `docs/LIVE_SCORE_MOTION.md`의 조회/강조 동작과 `docs/SCORE_ARROW_24H.md`의 24시간 변경 화살표 및 기존 승인 산식·화면 스타일을 보존한다.

## 3. 직접 원인·근본 원인

1. **목표 치환:** ‘사용자에게 보이는 점수 출력 규칙의 통일’을 ‘새 유효 원자료 감지와 과거 실제 이력 보존’이라는 별도 기술 과제로 혼동했다.
2. **계획의 자기강화:** 이력 과제 문서를 읽고 더 깊은 백엔드 계획을 작성한 뒤, 이후 `계속해라` 지시에 그 마지막 하위작업만 반복 연결했다. 최초 목표와 다시 대조하지 않았다.
3. **진행률 분모 오류:** 출력 UI의 검증 대상·승인 표현 기준을 집계하지 않고, `68개 전체 원자료→D1 종단 PASS`를 이 대화의 전체 진행률로 보고했다.
4. **브랜치/담당 경계 누락:** UI 정본 브랜치와 별도 backend 분리 자체는 맞을 수 있지만, UI 작업의 성공 기준을 보존하지 않고 backend 브랜치 업무만 이어갔다.
5. **중간 점검 실패:** D09/S01/D05 조사에서 ‘이 결과가 화면 출력 불일치의 어느 항목을 해결하는가?’를 확인하지 않아 목표 이탈이 누적됐다.

**근본 원인:** 최신 사용자 최종 산출물(출력 기준 통일)과 별도 데이터 플랫폼 과제(입력 갱신·일별 이력)를 실행계획 및 진척보고에서 독립적인 작업으로 구분하지 못했다. 이는 외부 API·Controller 장애가 아니라 **작업 범위 관리와 목표 재확인 실패**다.

- 본 대화의 활성 작업 기준을 이 문서의 **점수 출력 기준 통일**로 되돌린다. 기술 조사 자료를 삭제·rebase·reset하지 않고 별도 과제로 보존한다.

- UI 기준표에는 최소 `화면/컴포넌트 → 실제 값/API 필드 → 승인된 표시 변환/단위·정밀도 → 상태·날짜 → 기대 화면 → PC/모바일 검증`을 1행씩 기록한다. 미정 기준은 사용자 확정 없이 새 규칙으로 만들지 않는다.
- 작업마다 재시작 전 **한 문장 목표/현재 수정할 UI 범위/이번 변경이 없애는 실제 출력 불일치**만 확인한다. 새 공용 Controller Gate·예약·대형 사전검사를 추가하지 않는다.
- 이후 실제 UI 구현은 `codex/ui-improvements`에서 범위 최소 수정·테스트하고, 기존 Git 연동 배포 절차와 실제 화면을 검증한다. 다른 담당 기능의 수집·계산·배포는 건드리지 않는다.
