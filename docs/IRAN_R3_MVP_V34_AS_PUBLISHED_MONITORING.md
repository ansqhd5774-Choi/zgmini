## R34가 해결하는 관측 구분

R3 공개 `historyMode=RETROSPECTIVE_PUBLICATION_DATE` 및 차트 `dailyReferenceHistory`는 **기사 발표일을 기준으로 재구성한 점수**이다. 예를 들어 14일 차트의 7개 변화점은 **실제로 7번 공개 조회했다는 뜻이 아니다**. 화면용 carry-forward는 새로운 관측이나 무사건 입증이 아니다.

향후 R2·R3·R4 개선 비교는 공식 공개 GET 응답을 실제 조회한 시각별로 기록한 별도 observation 시리즈를 사용해야 한다. 최소 기준:

1. METHOD `IRAN_REFERENCE_FLOW_R3`, 조회시각, 공개시각, 수집 확인시각, 공개 점수, 업데이트 지연 상태를 묶어서 관측. 비밀번호·원문·원자료 저장 금지.
2. 같은 `publishedAt`에 점수가 바뀌면 **게시/버전 충돌**로 중단. 공개시각 역행도 중단. 새 게시가 있고 점수가 달라진 경우만 **실제 관측된 변화**로 센다.
3. 최초 1개 공개 조회만으로는 상승·하락 추세를 판단하지 않는다. 발표일 차트를 실제 공개값 시계열로 위장하지 않는다.
4. 지연일은 최신 확인값과 갱신 지연을 구분. 결측 0·50 보정 금지.
5. 방법 버전이 바뀌면 별도 계열로 분석하고 기존 R3 내역을 덮어쓰지 않는다.

연구 모듈 `lib/iran-progress/as-published-observation-v34.mjs`과 회귀 테스트는 **순수 데이터 비교만 수행**. 로컬 원장 저장/PC 일정 등록/공개 API 조회/게시/배포를 자동 실행하지 않는다.

## 운영 개선 단계

- **1차 운영:** 기존 R3 공개값 그대로 두고 실제 공개값 시계열 관측 시작.
- **2차:** 1차 관측에서 드러나는 갱신 지연, 점수 과포화, 사건 중복·잘못된 분류를 근거로 수정안을 승인·검증 후 최소 적용.
- **3차 이후:** 공식 해상/군사/핵/휴전 근거를 보강하여 R4를 독립 후보 비교. 승인 없이 기존 R3 가중치를 R4 후보 가중치로 바꾸지 않는다.

기존 GitHub main/D1/PC SQLite/산식/TTL/DNS/Cloudflare/scheduler 변경 없음. V33의 사용자 PC 검증과 연구 코드 통과는 Production 소스 전체 SHA나 모바일 UI 스크린샷 PASS를 뜻하지 않는다.
