## 4. 2단계 — 먼저 배포와 현재 동작을 확인

1. 최신 main과 관련 변경 파일을 필요한 범위에서 확인하고, 기존 Cloudflare Git integration의 활성 Production 산출물에 #1460/#1461/#1462의 필요한 변경이 실제 포함됐는지 확인한다. 이후 정상 배포가 포함할 수 있으므로 과거 각 PR의 개별 배포ID를 전부 찾는 작업을 새 완료조건으로 만들지 않는다.
2. 이미 포함돼 정상 동작하면 재배포·재병합·같은 fixture 재실행 없이 완료 증거로 사용한다. 자동배포가 아직 실행 중이면 해당 기존 실행을 확인하며 중복 배포를 만들지 않는다. Build 성공과 활성 Deployment/실제 기능을 구분한다.
3. 관련 UI/Reader 변경이 실제 누락됐으면 기존 브랜치의 해당 최소 diff만 정규 PR→main→Git integration 자동배포→실화면 순서로 반영한다. 이미 main에 있는 코드를 다시 다른 이름으로 재구현하지 않는다. direct Wrangler/Sites 배포·DNS 변경·전체 분기 브랜치 일괄 병합은 하지 않는다.
4. UI 정상 확인에 불필요한 PC source/DB 관리자권한 전수 확인을 강제하지 않는다. W06가 실제 UI에 소비한 공개 응답과 DOM/렌더링을 대조하고, D1/Writer 내부 동치는 원담당 별도 항목으로 남긴다. API HTTP200만으로 내부 운영 성공을 주장하지 않는다.
5. 자동화 GUI 접근이 실패하면 실제 서비스 오류로 판정하지 않는다. 기존 공식 GUI/실제 사용자 수동 Cross-Check로 확인하며, 이미 같은 버전의 실제 화면 PASS가 있으면 재검증하지 않는다. 유료 브라우저 크레딧 추가 구매·반복 접근 실패를 기본 작업으로 만들지 않는다.

## 7. 4단계 — 실제 PC·모바일 화면

영향 있는 활성 화면을 실제 PC1440px·모바일390px 또는 해당 기능의 기존 승인된 크기에서 확인한다. 별도 최소/최대 기기 전수 기준을 늘리지 않는다. 실제 카드 최신값/관측일과1D·1W·1M·3M·6M·1Y 중 영향받는 기간의 실제 마지막 점·축·단위·0·결측·부분이력·툴팁·연결선·가로 넘침을 공개 응답과 대조한다.

월간/분기와 시간별 실제 계산 관측을 혼합해 실제로 없는 일별 점을 만들지 않는다. 최종점이 같더라도 중간 이력이 완전하다고 주장하지 않는다. 숨겨진/퇴역 위젯과 원자료 미제공을 UI 계산으로 대신 만들지 않는다. 화면이 정상인데 스타일·점/선·색상을 임의 변경하지 않는다.

기존 유효한 실제 사용자 화면 확인은 완료 증거로 재사용한다. 새 사용자 검증이 필요할 때만 목적/준비 상태/화면·클릭·입력·횟수/기대값/STOP/금지행동/반환 결과를 구체적으로 요청한다. 같은 자동화 접근 실패를 반복하거나 자동화와 맞추려고 정상 수동 검증을 취소하지 않는다.

## 8. 5단계 — 두 종류의 완료를 분리해 종결

**W06 완료:** 소유 UI/Reader 결함 수정·관련 검사·필요 최소 main 반영·실제 적용·PC/모바일 기능 확인을 해당 근거로 판정한다. 그동안의 모든 소스 PR을 다시 감사하거나 관련 없는 전체 서비스 정상화를 요구하지 않는다.

4. **재조회 PASS 이후에만** 사용자에게 이번 결과와 **기록 반영 커밋**을 보고한다. 원장 쓰기 실패·충돌·불일치·도구 접근 차단 시 **`LEDGER_UNVERIFIED / 인계 미완료`**로 표시하며 작업 기능이 실제 수행됐더라도 전체 종료·인계 완료로 주장하지 않는다. 원장 수정이 허용된 범위라면 충돌 난 해당 파일만 새 SHA 기준으로 보존·재적용한다. 강제 push/reset/clean은 금지한다.
5. 아직 수행하지 않은 결과, 미래 예약 검증, 다른 대화의 자동 수신을 `DONE`으로 기록하지 않는다. 마지막 보고에는 **'진행 기록 원격 확인: PASS/미확정'**을 필수 기재한다.

### 4. 75단계 상태·진행률 판정

- `DONE`: 그 단계의 **계획서 완료 증거**가 실제 존재할 때만; `PARTIAL`: 코드/fixture만 있고 단계의 운영 통과조건 미충족; `READY`: 다음 실행 가능; `RUNNING`: 실제 진행 증거 확보; `STATE_UNKNOWN`: 런타임 확인 불가; `BLOCKED`: 해당 실행의 승인·권한·검증 차단; `DEFERRED`: 현재 필수 실행이 아닌 후속.
- 작업 항목의 성격이 분석·설계면 **소스·fixture·설계 증거만으로 해당 단계 DONE** 가능하나, 이를 운영 적용 DONE이라 확장하지 않는다. 개발·설치·게시 단계는 그 항목에 명시된 PC/공개 검증을 충족할 때만 DONE으로 계산한다.
- 진행률 = **서로 다른 DONE 단계 번호 개수 / 75 × 100**, 소수 첫째 자리 반올림. 부분·초안·CI 진행 중·미실행 항목은 분자 제외. 완성된 PR의 개수로 진행률을 증가시키지 않는다. **27개 D01–D27 각각의 최종 상태는 별도로** 유지한다.

### 5. 다른 대화/담당자의 재개 절차

1. `codex/ui-improvements` 최신 HEAD에서 **본 계획서 → 지정 진행 기록 맨 위 '현재 인계 정본' → 필요한 해당 실행 이력**만 읽는다. 이전 대화 문맥/채팅 첨부/타인의 진행 추측은 필수 입력이 아니다.
2. 완료 번호·증거·미완료 조건·관련 Draft/승인·소유권을 확인한다. **기존 성공 증거를 재사용**하고 source·config·환경 변경 또는 충돌 증거가 있을 때만 해당 범위를 재검증한다.
3. 진행 기록의 '다음 단 하나의 실행'부터 실제 가능한 일을 계속한다. 다른 담당자가 아직 받은 적 없는 GitHub 댓글을 자동 전달 완료로 가정하지 않는다. 공용 DB/Writer 등 동일 쓰기 자원만 직렬화한다.
4. 작업 종료 시 위 **3절 기록·커밋·재조회**를 재수행한다. 진행 기록이 최신 실작업과 충돌하면 **실제 증거를 우선해 정본부터 수정**하고 누락·변경 내역을 시간순으로 남긴다.

## 실제 수행의 병렬화/정지 원칙

- A/B의 소스/fixture/대상별 판정 및 UI 코드 검사는 서로 독립이면 병렬 진행. Core SQLite 동일 writer, D1 publish, 공용 lease/설치는 같은 lane만 직렬화.
- 수집/계산/게시 원담당과 W06의 실제 인계·승인 근거 없이 다른 대화가 자동 업무를 받았다고 가정하지 않음. 구현·병합·운영실증의 해당 담당을 구분.
- RUNNING은 로컬 저장·원장·checkpoint 실제 전진으로 판단. 개별 최신 자료 없으면 유효 마지막 값을 유지하되 새 관측이라고 위장하지 않음.
- 75번 완료 시 **사용자에게 홈페이지 직접 확인 요청**. 그 이전에는 웹디버그나 수동 PC 작업/화면 확인을 사용자에게 요구하지 않음.
