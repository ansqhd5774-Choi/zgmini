## 0. 목적 / 왜 기존 3·5·7단계가 부적절했는가

**사용자 질문:** "산식에 해당되는 지표가 수집되면 점수를 곧바로 출력하는지, 산출 기간이 되어야 출력하는지?"의 **실제 기능별 답을 확인**하고, 승인 산식이 허용하는데도 불필요한 날짜 대기로 갱신되지 않는 경로 및 동일 공개값에 대한 잘못된 표시만 수정한다.

`수집 직후`를 무조건 즉시 화면 표시하라는 의미로 해석하지 않는다. 승인된 기존 실행 경로의 **다음 계산/저장/게시 성공 시점**에 현재 점수로 반영한다. 승인된 완료월/완료분기·전체 READY·거래일·잠정/확정 조건은 보존하고, 지표별 공표주기는 강제로 일치시키지 않는다. 브라우저 60초 재조회와 계산 일정은 별개다.

**제외(기존 별도 작업 보존):** D05 입력 SHA·원장 25건의 추가 조사, 과거 계산 사건의 완전한 인과 추적, 새 score history/revision/DB/D1 스키마 설계, 1Y 불변 PIT 복구, 섹터 11개/테마 30개의 등록·수집·산식 개발, 68개 전수 PC 종단 검사, 기존 정상이던 기능의 재설치·재검증. 특정 출력 오류를 설명하는 데 직접 필요한 사실만 해당 기능의 기존 원장 1건을 조회한다.

**최종 수락:** 기존 27개 콘텐츠의 갱신 방식 분류 27/27; 수정 필요 결함군을 빠짐없이 기록하고 각 군의 승인된 최소 코드·관련 테스트·해당 운영 게시/UI 결과까지 PASS; 기존 정상/기간 대기는 별도 변경 없이 종결. D03/D04는 비율형, D26/D27은 보조 콘텐츠이므로 새 0–100 산식으로 바꾸거나 25개 홈 카드로 오인하지 않는다.

## 1. 작업 단위·진행률 설계

- **고정 34개:** 공통 준비 `01–03`(3개), D01–D27별 갱신 조건 독립 판정 `04–30`(27개), 혼합 주기 시나리오 `31–32`(2개), 실제 결함군 확정·종결 `33–34`(2개).
- **변동분 4×N개:** `33`에서 승인 조건을 잘못 적용하거나 UI 상태를 잘못 표시하는 **서로 독립된 원인**이 실제 확인되면 결함군마다 `F1 재현/영향`, `F2 최소 수정`, `F3 영향 회귀`, `F4 실제 승인 적용·API/UI 검증`을 추가. 동일 root-cause와 공유 소비자면 한 군, 다른 원인이면 분리.
- **실행 작업 총수:** `34 + 4×N`; `N`은 단계 33에서 확정하는 실제 결함군 수. 실증 전 N을 0이라고 단정하거나 34개로 고정 보고하지 않는다.
- **진행률:** `(완료 증거 있는 고정 항목 + 완료 증거 있는 추가 항목) / (34 + 4N)`을 단계 33 이후 확정 계산한다. 그 전에는 `고정 항목 x/34`, `분류 y/27`, `결함 z건(잠정)`을 별도 보고한다. 기존 68/68 콘텐츠 식별은 **자료 재사용 실적**이지 분류 27/27 완료가 아니다. 소스 확인과 운영 적용을 같은 PASS로 세지 않는다.
- **각 단위의 증거:** 조회한 현재 코드/API/승인 Gate, 기대 갱신 시점, 실제 갱신 또는 올바른 대기, 상태(정상/결함/미연결/미확인/기간 대기), 수정 소유자. 누락 필드는 UNKNOWN으로 남기되, 불필요한 PC 전체 진단을 새로 요구하지 않는다.

F4는 UI만 변경이면 정규 배포·페이지 표시 증거, PC 계산/게시 변경이면 기존 Owner의 승인 PC 적용·저장·D1/API/UI 증거만 수집한다. **새 날짜의 자연 발생을 기다리는 예약 관찰·전역 Runner 유휴·Controller 전체 재설치**를 새 종료 조건으로 만들지 않는다. 범위 밖 DB·스키마·산식 변경이 실제 필요한 경우만 정확한 승인 내용을 제시한다.

## 6. 소스 경계·기존 완료·하지 않을 일

- 기존 R1에서 **대상 식별 27/27** 및 API 계약 초안 확보; 2026-11-10 관측치를 오늘의 최신값으로 사용하지 않는다.
- D05 `current.stored_at` 계보 위험은 별도 분석; 이전 가짜 입력 3건 PASS 및 PC `d05-lineage-readonly` 원장 25건 확인은 **이번 27개 갱신 조건 판정 완료 실적이 아니다**. 새 원장·서명 구축을 이번 목적의 Gate로 요구하지 않는다.
- 계산의 `input signature`, 기존 사업부의 history/revision/원자료 추적은 별도 `codex/dashboard-score-daily-r1` 백엔드 과제로 보존한다. 승인 없이 중단/수정/병합하지 않는다.
- 정상 설계인 완료월·완료분기·READY·거래일은 해제하지 않는다. D05 화면 민감도 3.5, D08 별도 `stagflationSafety`, D03/D04 비율형, D27 R13 예약 제거를 보호한다.
- W06이 상대 Owner의 승인 없는 PC 파일·Controller·DB/공용 lease에 직접 쓰지 않는다. UI 관련 구현은 W06 브랜치에서 직접 수정한다.
- 테스트와 릴리스는 해당 변경 범위에 비례한다. 실제 변경이 없다면 무작정 브라우저·PC 상태 전체 점검을 하지 않는다.

## 7. 현실적인 첫 후속 작업 하나
